## 4. Modules & Features

### 4.1 Authentication (`apps/api/src/modules/auth`)

**Purpose:** the product's one door — a mobile number and a one-time code, no
passwords.

**Features:**
- Sign in and sign up in one flow, branching on whether the number is known.
- One live code per number: single-use, expiring, attempt-limited, rate-limited.
- Cookie sessions, issued and cleared by the backend.

### 4.2 Admin panel (`apps/admin`, `modules/admin-auth`, `modules/admin-users`)

**Purpose:** the staff-facing surface. A desktop dashboard, responsive down to
a phone, behind a username and a password.

**Features:**
- Admin sign-in, with account status, access expiry and a forced first-time
  password change all decided by the backend.
- Role-based access: permissions per role, checked in the UI for convenience
  and in the API for real.
- «مدیریت کاربران» — create, view, edit, re-role, expire, suspend and reset
  admin accounts.
- Temporary passwords: generated by the backend, stored only as a hash, sent by
  SMS, replaced rather than recovered.

### 4.3 Forms & surveys (`modules/forms`, both apps)

**Purpose:** admins build forms and surveys; people in the product answer them.

**Features:**
- A dashboard of every form, with counts, search, status filter and sort.
- A three-column builder: 25 question types, drag and drop, pages, welcome and
  thank-you screens, per-question background images, autosave.
- Conditional logic — show, hide, jump to a page, end the form — written as
  readable rules.
- Per-form settings: availability window, audience, response rules,
  notifications.
- Publish to an internal link, `{WEB_BASE_URL}/forms/{id}`.
- A respondent page in the product with no product navigation around it.
- Responses: overview, per-question analysis, individual answers, CSV/Excel
  export and print-to-PDF.

Everything else in §4 is unwritten: the remaining modules are mounted and empty.

### 4.3 App shell

**Purpose:** The frame every signed-in screen renders inside.

**Features:**
- A header carrying the product name, the theme toggle and the account menu
  (name, phone, sign out).
- A sidebar with the navigation, collapsible to icons; the choice is
  remembered.

**Not built yet:** the sidebar is tablet-and-up. The drawer that used to bring
it onto a phone was opened by a hamburger in the header and by nothing else, so
both went together — a phone currently has no navigation chrome, which is
workable while the product is one screen and needs an answer before it is more.

## 5. User Flows

### 5.1 Sign in / sign up

There is one door into the product, at `/login`, and no passwords. Full detail
in [architecture/auth-flow.md](./architecture/auth-flow.md).

```
User opens the app
  |
  +-- enters a mobile number
  |     |
  |     +-- the backend checks whether it is registered
  |
  +-- registered ──→ a 4-digit code is sent
  |                    |
  |                    +-- enters the code  ──→ signed in
  |
  +-- not registered ─→ registration form (name, surname, date of birth in the
  |                      Jalali calendar, gender)
                         |
                         +-- a 4-digit code is sent
                              |
                              +-- enters the code ──→ account created ──→ signed in
```

On the code screen the user sees the number the code went to, a two-minute
countdown, a resend that unlocks when the countdown ends, and **ویرایش شماره**,
which cancels the code in flight and returns to the first step.

A user account exists only after a code has been verified. Submitting the
registration form on its own creates nothing.

### 5.2 Admin sign in

The admin panel (`apps/admin`, port 3001) is a different product with a
different door. Full detail in
[architecture/admin-auth-flow.md](./architecture/admin-auth-flow.md).

```
Admin opens the panel
  |
  +-- username + password ──→ the backend checks, in this order:
  |                             the password, the account's status, its access
  |                             expiry date, and whether its password is still
  |                             a temporary one
  |
  +-- must change password ──→ /change-password, and nothing else works
  |                              |
  |                              +-- new password (8+, upper, lower, digit,
  |                                  special) ──→ dashboard
  |
  +-- otherwise ─────────────→ dashboard
```

There is **no self-registration and no password recovery**. An admin account is
created by another admin, which generates a six-digit temporary password and
texts it with the username. A forgotten password is answered by replacing it,
never by revealing it — only a hash is stored.

### 5.4 Building and answering a form

```
Admin: /forms  ──"ساخت فرم جدید"──→  blank, or one of six templates
                                        │
                              /forms/{id}/edit  (builder, autosaving)
                                        │
                                    انتشار  ──→  link: /forms/{id}
                                                     │
People in the product:  open the link ──→ answer ──→ «پاسخ شما با موفقیت ثبت شد.»
                                                     │
Admin: /forms/{id}/responses  ←──────────────────────┘
        overview · per-question analysis · individual answers · export
```

A form is answerable only while it is published **and** inside its availability
window, and only by whoever its audience allows. All three are decided by
`apps/api` on every request — the link by itself grants nothing. Full detail in
[architecture/forms-module.md](./architecture/forms-module.md).

### 5.3 Managing admin users

«مدیریت کاربران» in the panel lists the admin accounts, with search and
paging, and offers: create a user, view and edit their details, change their
role, change their access expiry, suspend or reactivate them, and reset their
temporary password (which also re-sends their credentials, because those are the
same operation).

Every admin has a role, and a role carries permissions. The panel hides what a
role cannot reach; `apps/api` refuses it. Both exist on purpose — the first is a
convenience, the second is the boundary.

## 6. Data Model

No database has been chosen, so nothing here is implemented. What is designed:

### 6.1 Entity Relationship Diagram

```
+------------+       +--------------------------+
|    User    |--1:N--|         Session          |
+------------+       +--------------------------+
      |
      | by phone number, not by key
      |
+--------------------------+
|  VerificationChallenge   |   at most one live per number
+--------------------------+
```

### 6.2 Key Relationships

- A **User** has many **Sessions**; deleting the user ends all of them.
- A **VerificationChallenge** belongs to a phone *number*, not to a user — a
  code is issued before an account exists, which is what lets registration
  require a verified phone.

Admin accounts are a separate design — an admin is not a `User` with a role:

```
+------------------------------+       +--------------------------+
|         AdminUser            |--1:N--|      AdminSession        |
+------------------------------+       +--------------------------+
              |
              | by role code, not by key (the catalogue is in code today)
              |
+------------------------------+
|         AdminRole            |
+------------------------------+
```

Forms are the third design, and the one that is not a set of columns:

```
+------------------+       +--------------------------+
|      Form        |--1:N--|      FormResponse        |
+------------------+       +--------------------------+
  pages, questions, logic, audience and settings are JSON on the form —
  they are always read and written together, by the builder and by the
  respondent's screen alike.

+------------------+
|  FormTemplate    |   copied into a new form, never referenced by one
+------------------+
```

Fields, constraints, indexes and the lifecycle of each entity are in
[architecture/auth-data-model.md](./architecture/auth-data-model.md) for the
product's users,
[architecture/admin-data-model.md](./architecture/admin-data-model.md) for the
panel's, and
[architecture/forms-data-model.md](./architecture/forms-data-model.md) for forms
and their responses. Nothing else is designed yet.

## 7. API Endpoints

### 7.1 REST API Routes

`apps/api`, mounted under `/api/v1`. Reference:
[api/auth.md](./api/auth.md), [api/admin-auth.md](./api/admin-auth.md),
[api/admin-users.md](./api/admin-users.md) and [api/forms.md](./api/forms.md).

| Method | Endpoint                 | Description                                  |
|--------|--------------------------|----------------------------------------------|
| GET    | `/health`                | Liveness probe, outside the version prefix   |
| POST   | `/api/v1/auth/check-phone` | Is this number registered?                 |
| POST   | `/api/v1/auth/register`  | Hold a new user's profile, send a code       |
| POST   | `/api/v1/auth/otp/send`  | Send a code — and, called again, the resend  |
| POST   | `/api/v1/auth/otp/verify`| Verify a code: creates the session           |
| POST   | `/api/v1/auth/otp/cancel`| Cancel the code in flight (ویرایش شماره)     |
| GET    | `/api/v1/auth/session`   | Who the session cookie belongs to            |
| POST   | `/api/v1/auth/logout`    | Invalidate the session                       |

The admin panel, reference: [api/admin-auth.md](./api/admin-auth.md) and
[api/admin-users.md](./api/admin-users.md).

| Method | Endpoint                                  | Description                                  |
|--------|-------------------------------------------|----------------------------------------------|
| POST   | `/api/v1/admin/auth/login`                | Username + password; creates the session     |
| POST   | `/api/v1/admin/auth/change-password`      | The forced change; rotates the session       |
| GET    | `/api/v1/admin/auth/session`              | Who the cookie belongs to, and what they may do |
| POST   | `/api/v1/admin/auth/logout`               | Invalidate the session                       |
| GET    | `/api/v1/admin/users`                     | List admin accounts (search, paging)         |
| POST   | `/api/v1/admin/users`                     | Create one; generates and texts a password   |
| GET    | `/api/v1/admin/users/:id`                 | One account                                  |
| PATCH  | `/api/v1/admin/users/:id`                 | Details, role, access expiry, status         |
| POST   | `/api/v1/admin/users/:id/reset-password`  | New temporary password, texted               |
| GET    | `/api/v1/admin/forms`                     | The forms dashboard (search, filter, sort)   |
| POST   | `/api/v1/admin/forms`                     | Create one, blank or from a template         |
| GET    | `/api/v1/admin/forms/overview`            | The four summary cards                       |
| GET    | `/api/v1/admin/forms/templates`           | The starting points                          |
| PATCH  | `/api/v1/admin/forms/:id`                 | The builder's autosave                       |
| POST   | `/api/v1/admin/forms/:id/publish`         | Publish, unpublish, close, duplicate         |
| POST   | `/api/v1/admin/forms/:id/assets`          | Upload a question's background image         |
| GET    | `/api/v1/admin/forms/:id/responses/stats` | Statistics over every response               |
| GET    | `/api/v1/admin/forms/:id/responses/export`| CSV / Excel download                         |
| GET    | `/api/v1/forms/:id`                       | A published form, for whoever may answer it  |
| POST   | `/api/v1/forms/:id/responses`             | Submit answers                               |

Every other module (`users`, `worlds`, `content`, …) is mounted and empty.

### 7.2 Server Actions (RPC)

None. The front-end reaches the backend through `src/services` over HTTP, so
there is one request path rather than two.
