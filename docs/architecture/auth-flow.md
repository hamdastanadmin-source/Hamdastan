# Authentication flow

Sign-in is passwordless. A user types a mobile number, receives a four-digit
code, and is signed in once that code is verified. There are no passwords and
no usernames anywhere in the product.

Everything that decides anything lives in `apps/api`. The web app renders the
steps and holds no rules of its own — which is what makes the flow the same
whichever client is talking.

---

## 1. The two paths

```
                     ┌─ registered ──→ send code ─→ verify ─→ signed in
phone → check-phone ─┤
                     └─ unknown ────→ registration form ─→ send code ─→ verify
                                                                          │
                                                          create the user ┘
```

Which path a number takes is decided by the backend, from the state of that
number. The client never asks for one: it cannot request a registration code
for a number that already has an account, or a sign-in code for one that does
not.

### Existing user

```
POST /auth/check-phone   { registered: true }
POST /auth/otp/send      a code is generated, hashed and delivered
POST /auth/otp/verify    the challenge is destroyed, a session is created
```

### New user

```
POST /auth/check-phone   { registered: false }
POST /auth/register      the profile is held as a draft; a code is delivered
POST /auth/otp/verify    the draft becomes a user, then a session is created
```

The form collects the date of birth in the **Jalali** calendar — three
dropdowns, because a native date input renders in the browser's own calendar,
which for a Persian user is the wrong one. It is converted to an ISO Gregorian
date by `packages/shared/format/jalali.ts` before the request, so the backend
and `birthDateSchema` only ever see `YYYY-MM-DD`.

The year list runs from `BIRTH_YEAR_MIN_JALALI` (۱۳۲۰) to the current Jalali
year, newest first, and within the current year the months and days stop at
today. There is no minimum age. Nothing the dropdowns can assemble fails
validation, which is the point of deriving both from one rule:
`birthDateSchema` rejects anything before 1 Farvardin ۱۳۲۰ or in the future,
and the list is built from the same bound.

**Submitting the registration form does not create a user.** The profile —
first name, last name, date of birth, gender — is held on the challenge and
becomes a `User` row only inside a successful verification. If the code is
never verified, the draft expires with the challenge and nothing is left
behind, so an unverified user cannot exist.

## 2. Code lifecycle

| Rule | Where it is enforced |
| --- | --- |
| Generated by `randomInt`, in the backend, never accepted from a client | `auth.service.ts` |
| Four digits | `OTP_CODE_LENGTH` in `packages/validation/auth.ts` — the generator, the validator and the boxes on screen all read it |
| Valid for `OTP_TTL_SECONDS` (120) | `issueChallenge`, checked again in `verifyOtp` |
| Only the SHA-256 hash of `phone:code` is stored, in every environment | `hashCode`; `OtpChallengeRecord` has no field for a code |
| Single use — destroyed on success, before the session exists | `verifyOtp` |
| Invalidated by the next code for that number | one challenge row per phone, overwritten |
| Invalidated when the user edits their number | `POST /auth/otp/cancel` |
| At most `OTP_MAX_ATTEMPTS` (5) wrong guesses, then locked | `attempts` counter |
| No resend until the countdown ends | `resendAvailableAt` |
| At most `OTP_MAX_SENDS` (5) codes per `OTP_SEND_WINDOW_MINUTES` (15) | `sendCount` + `windowStartedAt` |

A resend is the same call as the first send — `POST /auth/otp/send` — so there
is no second path to a code that could skip the cooldown or the limit. A resent
code starts with a clean set of attempts, because the code it replaces is dead.

The countdown the user watches is a courtesy, not a rule. An expired code is
refused by the backend whatever the screen says.

---

## 3. Editing the number

The verify screen shows the number the code went to and a **ویرایش شماره**
link. Choosing it:

1. calls `POST /auth/otp/cancel`, which deletes the live challenge — the code
   already sitting in the user's messages stops working immediately rather than
   staying valid for the rest of its two minutes;
2. returns to step one with the field prefilled;
3. starts over from `check-phone`, so a number that was going to register can
   turn out to be one that signs in.

Because the challenge is gone rather than expired, the new number is not held
behind the old cooldown.

## 4. Sessions

A verified code creates a session: 256 bits of randomness, stored by the
backend against the user, and set on the browser as an httpOnly cookie. The
token never appears in a response body.

```
verify ──→ apps/api sets `session=…`  (httpOnly, SameSite=Lax, Secure in production)
           │
           ├─ browser → apps/api        the cookie rides along automatically
           └─ apps/web rendering        reads the cookie and forwards it to
                                        GET /auth/session
```

`apps/web` stores nothing. `getSession()` in
`apps/web/src/features/auth/services/session.service.ts` reads the cookie and
asks the backend who it belongs to; `requireAuth()` and `requireAdmin()` are
built on it. If the backend cannot be reached, the visitor renders as signed
out rather than the page failing — recoverable, where a 500 on every route is
not.

Signing out goes from the browser straight to `POST /auth/logout`, because the
backend is what issued the cookie and the only thing that can invalidate the
token behind it. Clearing the cookie alone would leave a usable session on the
server.

### Cookie scope

Locally the web app is on `:3000` and the API on `:4000`. Cookies ignore
ports, so a host-only cookie is shared between them, and the two are same-site,
so `SameSite=Lax` still carries it. In production they are sibling hosts, so the
cookie has to be scoped to the parent domain — set `SESSION_COOKIE_DOMAIN`
(e.g. `.hamdastan.ir`). `CORS_ORIGINS` must list the web origins, since the
browser only sends credentials to origins the API echoes back.

## 5. Delivery

No SMS gateway is contracted yet. Delivery sits behind an adapter in
`apps/api/src/integrations/otp/`:

```
auth.service ─→ otpProvider() ─→ MockOtpProvider   (writes the code to the log)
                                 └── a real gateway goes here
```

The service depends on the `OtpProvider` interface, not on a vendor, so a real
gateway is one more implementation plus a change to `OTP_PROVIDER`. No business
logic moves. See [external SMS integration](./auth-sms-integration.md).

### Walking the flow without a gateway

With `SHOW_DEV_OTP=true` and `NODE_ENV` other than `production`, the backend
echoes the generated code back in the challenge response, and the verify screen
shows it as **کد تست**. The code is still generated by the backend and still
subject to every rule above — only its visibility changes.

`env.showDevOtp` is `SHOW_DEV_OTP && !isProduction`, so production cannot switch
it on, whatever the environment says. The front-end has no code generator of its
own: it renders `devCode` if the backend sent one and shows nothing if it did
not.

The echo is attached to the *response that issues* the code, not to the stored
challenge — `OtpChallengeRecord` has nowhere to put a code. So switching the
flag on cannot write a usable code into a row, which matters the moment the
in-memory store is replaced by a database in a staging environment.

| Session reading and route guards | `apps/web/src/features/auth/services/session.service.ts` |

`/login` renders `<AuthFlow />` and nothing else. The step order lives in
`use-auth-flow.ts`; the steps themselves render what it gives them.

Expiry and "a resend invalidates the previous code" are covered in the service
tests with a controlled clock rather than in the browser, where they would cost
the full two minutes each.

## 8. Known limits

Two things are deliberately left where they are, and should be settled before
this carries real traffic.

**A four-digit code is 10,000 possibilities, not a million.** What makes that
safe is not the code's length but the limits around it: five wrong guesses lock
the challenge, a new code cannot be had until the countdown ends, and no number
gets more than `OTP_MAX_SENDS` codes per window. Those three together cap a
guessing attack at roughly 25 tries per quarter hour — about one chance in four
hundred of landing a specific code, per hour of trying. Lengthening the code is
the lever if that ever stops being acceptable; loosening `OTP_MAX_ATTEMPTS` is
the one that would make it unacceptable.

**The send limit lives on the challenge.** `sendCount` and `windowStartedAt` are
fields of the live challenge row, and both a successful verification and
**ویرایش شماره** delete that row. Resetting on a successful sign-in is intended;
resetting on a cancel is not — it means the `OTP_MAX_SENDS` window can be
restarted by cancelling between sends, so the limit holds for the ordinary
resend path but is not an abuse control. The counter needs a lifetime of its own
(its own pair on the port, or a throttle at the edge keyed on the normalised
number) before it can be called one.

**Nothing authenticates a route but this module.** `GET /auth/session` reads the
cookie in `auth.controller.ts`. When a second module needs a protected route,
that belongs in a `preHandler` in `apps/api/src/middleware/` that decorates
`request.user`, rather than being copied.

## 9. Error codes

The UI switches on `code`, never on the message text. `AuthErrorCode` in
`packages/types/auth.ts` is the list; `docs/api/auth.md` maps each one to a
status and a message.
